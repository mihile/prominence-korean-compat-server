# Voxy streaming allocation and secondary-cache bounds

Server build2026110306 adds two guarded, server-only changes based on a 120-second JFR capture and a post-recording live-object HPROF analyzed in Eclipse MAT.

`LodStreamingService.serializeSection` requests `WorldSection.copyData()` for each section. Each native section contains32,768 longs; a copy allocates262,160 bytes on the tested JVM. The method uses this array only as temporary input for its independently owned short-index/LUT payload and does not retain it. A narrow redirect instead calls the existing native `copyDataTo` into a thread-local32,768-long buffer. It retains no world or section reference. The existing native lifetime assertions/copy behavior remain; network payload arrays, hash, registry mapping, ordering and protocol remain native. The buffer is private to each calling thread, bounded at256KiB per active streaming thread. Native serializer code has no reentrant serialization call.

`WorldEngine` normally selects a secondary-cache capacity of2,048 sections when max Java heap exceeds approximately3.8GiB. That decision does not consider physical RAM consumed by a colocated client. The exact two-argument constructor's `ActiveSectionTracker` call now receives at most512 secondary sections. Live referenced sections are not capped. Native eviction/reload and persistent storage remain intact. This bounds that cache's section arrays near128MiB instead of512MiB when filled, a theoretical384MiB saving. Array reuse pools, other metadata/caches and active sections remain additional memory; this is not a measured384MiB process-memory reduction. Less secondary caching can increase storage reads on repeat visits.

Override: JVM property `prominence.voxy.secondaryCacheSections`; positive values are bounded to64..2048 and never increase the native capacity.0 or a negative value preserves the native capacity. This release does not edit JVM arguments or operating configuration.

Guards pin the installed WorldSection, WorldEngine and ActiveSectionTracker class hashes and either reviewed VoxyServer port.1/port.2 streaming-class hash. The capture actually ran port.1 despite both files being present. No third-party JAR is replaced or deleted by this change. Existing server compatibility classes and updater bytes remain unchanged. Failure to match pins disables this module.

Validation: real Mixin transformations and ASM verification against both installed VoxyServer versions;315 checks using native Voxy classes for bit-identical copies, same-thread reuse, distinct-thread isolation, active-section lifetime,512-section native cache bounds and successful evicted-section reload. A ThreadMXBean measurement over1,000 escaped native copies reports262,160,000 baseline allocated bytes versus0 for the warmed scratch branch. This measures the copy branch only, not whole-server allocation or gameplay improvement. The cumulative updater suite and bytecode checks also pass. No Minecraft server/world is launched by these fixtures.

The timed recording's initial-login spike also includes native entity ticks, first registry/reward synchronization and cold mapper loading. Later streaming allocation and the bounded cache are proven optimization targets; this release does not claim to eliminate every login spike. Next-start application and another capture are required for production validation.
