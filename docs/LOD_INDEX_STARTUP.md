# Default-world LOD index preparation at startup

Build2026110310 queues the existing native default-world presence-index preparation immediately after VoxyServer's dedicated-server startup callback has initialized its engine and streaming service. In the observed captures, the1,118,010-section scan repeatedly started after the first client became ready and took12–19seconds on the streaming thread. Its duration is not a server-thread pause measurement. This change shifts that scan earlier so it can complete before first login; it does not eliminate the scan cost or prove that all recorded backlog was caused by it.

The server thread captures only the already available default world's WorldIdentifier and dimension identifier. The job uses the existing service-owned streaming ExecutorService; it does not create another executor or perform DB opening/scanning inline on the server thread. The job calls existing getOrCreate and prepareStoredSectionPresence through a narrow invoker. Native presence states, concurrent dirty additions, acquire/release reference handling, exception/failure fallback and storage iteration remain unchanged. Existing heartbeat updates remain active during the scan.

Only the default world is requested. Other dimensions remain lazy. Duplicate startup requests per streaming-service instance coalesce. Executor shutdown/rejection is respected; no worker is resurrected. Already-interrupted jobs do nothing. Runtime preparation failures are nonfatal; normal streaming remains the fallback. The task contains no direct MinecraftServer or ServerWorld field. It changes no LOD format, generation range, packet gates, gameplay settings or chunk-generation rules.

Tradeoff: the server now opens/reads the default-world LOD database earlier and can spend disk/CPU resources preparing an index even if no player uses LOD that session. The native index/filter/cache may become resident earlier. If a player joins immediately, preparation may still overlap login. The native world cleaner may later close an idle WorldEngine, so this does not promise that all mapper/DB opening costs remain warm forever. No persistent new index file is written by this module; the normal native storage implementation is used. Set JVM property `prominence.voxy.startupIndex=false` to retain the previous lazy behavior. The release does not edit JVM arguments.

Guards pin Minecraft1.20.1 plus exact reviewed Voxyserver, LodStreamingService, ServerLodEngine, WorldIdentifier and WorldEngine class hashes, with the installed port.1/port.2 variants supported. New duck interfaces are outside the Mixin package. Existing compatibility classes and updater bytes are preserved.

Validation: all three native startup/service/invoker transformations and ASM checks pass for both installed VoxyServer variants.21 production scheduler/task checks use small API/executor doubles to cover safe-thread capture, no inline scan, duplicate requests, immutable identifiers, heartbeat, independent services, missing identity/world, rejected/shutdown executor, interruption and nonfatal failure. The native scan itself is delegated rather than reimplemented; these fixtures do not measure real RocksDB performance or run a Minecraft world. Cumulative132 updater checks,236-class/1,208-method verification and previous11 guard checks pass. Production login timing remains a next-normal-start capture check.
