# Reward display preparation before first login

Build2026110308 adds a server initializer that queues preparation at Fabric SERVER_STARTED and executes it once at the first END_SERVER_TICK on the server thread. Delaying to that tick ensures all SERVER_STARTED listeners have returned and avoids the network-addon's constructor phase. It uses weak server keys, coalesces duplicate starts, separates server identities and removes lifecycle state at SERVER_STOPPED.

Preparation calls the existing RewardRegistry.snapshot with the server recipe manager, then the existing RewardWire modern and legacy payload caches. No player or network call is made. Normal REGISTER/JOIN/send callbacks, negotiated channels, per-connection deduplication, actual drop math, registry indexing, codec bounds and reload invalidation are unchanged. Later login uses the same cached list/bytes when its resource epoch has not changed. A later reload still follows the existing snapshot/cache fallback.

This moves lazy recipe-reference scanning, display descriptor creation, class initialization, JSON serialization and GZIP compression away from the first player login. It does not eliminate that work or make all startup cheaper. Metadata and ingredient caches become resident earlier; warming the legacy schema may retain up to one extra bounded compressed packet (normally a few hundred KB). A player joining before the first safe startup tick can still use the existing lazy path.

Runtime preparation failures are nonfatal and are not retried every tick. Normal lazy login preparation remains available. No asynchronous reads of mutable server data, forced GC, heap dump, server restart or settings changes are introduced.
